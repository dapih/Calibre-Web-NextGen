# Native Windows M0 proof progress

This is an initial proof probe, not an installer or a passed release gate. The authoritative acceptance criteria are in the [approved specification](https://github.com/dapih/Calibre-Web-NextGen/blob/bd8cc31f48915f2c346db748d6c1478870257378/docs/install/windows-native-specification.md).

On 2026-11-04, Windows x64 build 26300 was used to run `scripts/windows-m0-n1.ps1 -BuildFaust`. The probe downloaded the repository-pinned python-build-standalone CPython 3.13.14 (release 20260623), verified SHA-256 `646254b53fbac69c1b3c25131c237c9136e9bbed7444123880cea8deaf555e1f`, extracted it under the ignored `.m0` directory, and ran it with Python isolated mode. Its reported interpreter and Python import paths were inside that private tree.

The faust-cchardet 2.1.19 source download and build-dependency preparation succeeded, but wheel compilation failed because Microsoft Visual C++ 14.0 or later was unavailable. No `cl`, Visual Studio Installer `vswhere`, or usable `py` launcher was found during the initial probe. This establishes a missing build prerequisite on this machine; it does not establish whether the package can compile once a compiler is available. The exploratory pip build did not lock build dependencies and is not a reproducible build.

**N1 remains pending.** The subsequent MinGW experiment below overcomes the immediate local compiler gap, but must be reproduced on a clean controlled Windows machine and followed by the full dependency, tool, asset and poisoned-environment checks. N2–N6 also remain pending; no process-containment, all-writer, durability, Linux regression or native book-pipeline proof has been run. Do not begin installer/payload commitment on the basis of this probe.

The probe keeps its Python tree, pip cache, temporary build files and wheels under `.m0`; it does not install Python or packages globally. It now verifies the source archive hash and installs explicitly pinned, hash-checked build dependencies into a private build environment. A second local attempt installed those dependencies and passed `pip check`, then failed at the same missing Microsoft C++ compiler. The selected build dependency versions are experimental, not yet a validated release lock.

On the same machine, a workspace-local [MinGW-Builds GCC 16.2.0 archive](https://github.com/niXman/mingw-builds-binaries/releases/tag/16.2.0-rt_v14-rev1) was checked against its published SHA-256 `26788998d615856a915e1eeacb0854fce87bc608fa9a0c16f96bcbfdcf3415c0`. Using that compiler, the locked build produced `faust_cchardet-2.1.19-cp313-cp313-win_amd64.whl`, SHA-256 `15184bbeab58be550a829b1e08ab8dbcd714285bd1d618eadbc888eab3f05459`. That wheel did **not** import by itself: its extension requires MinGW runtime DLLs `libgcc_s_seh-1.dll`, `libstdc++-6.dll` and `libwinpthread-1.dll`. After copying those three DLLs into the private test package directory, import and basic ASCII/UTF-8 detection passed with the compiler excluded from PATH and poisoned `PYTHONHOME`/`PYTHONPATH`; the Windows loader reported all three DLLs in the private test directory. The experiment did not produce a self-contained distributable wheel. DLL redistribution, collision handling, complete encodings/metadata tests and full payload isolation remain open.

Two initial builds produced different wheel hashes; comparison found ZIP timestamps and bytes in the compiled extension, including its PE timestamp and checksum, differed. Three subsequent builds on this same machine with `SOURCE_DATE_EPOCH=1782160000` and linker flag `--no-insert-timestamp` produced the identical wheel SHA-256 `ce05053b3fb909228ba460dbd78077515124546d4cc39af31b9810d88b83c486`. They passed the same basic private-DLL tests; the final run also verified the loaded DLL paths and restoration of the caller's environment. This is evidence of repeatability in one workspace, not yet reproducibility across clean machines or a complete distributable dependency. The probe now applies those settings for `-BuildFaust -Compiler Mingw` and restores its process environment on exit. The verified compiler archive and extracted tree must already be present under `.m0` for that option.

The fork is public, while the approved first-release policy keeps incomplete proof artifacts internal; the proof files and binary outputs remain local. All N1–N6 gates remain pending. A private/controlled build environment and the other specified native, Linux and end-to-end checks are still required.

To repeat this local experiment from the worktree, run `./scripts/windows-m0-fetch-mingw.ps1` and then `./scripts/windows-m0-n1.ps1 -BuildFaust -Compiler Mingw`. The first script downloads and verifies the pinned compiler archive before extraction; the second verifies the pinned Python and Faust source archives, reinstalls the hash-locked build dependencies in a private environment, and builds/tests the wheel. The compiler archive is about 108 MB before extraction. An already extracted compiler tree is reused, so a clean independent build must also verify or recreate that tree. The scripts are experiments, not a released installation method.

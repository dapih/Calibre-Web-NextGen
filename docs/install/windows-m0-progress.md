> **Current status (2026-11-06):** N1–N6 pass for the local M0 proof. Validate the supported per-user installation and ordinary duplicate launches with the available Windows account. No other account, session, machine or VM is required, and no test requires installing or enabling Docker or WSL. ## DLL collision negative control — 2026-11-05

`scripts/windows-m0-faust-collision.ps1` reproduced a hole in the copied-DLL arrangement on this same Windows machine. It copies the test package into a fresh disposable `.m0` directory, removes that copy's `libgcc_s_seh-1.dll`, preloads the same-named DLL by absolute path from the compiler tree, removes the compiler from PATH, poisons Python environment variables and imports the copied package with `-I -S`. Import and ASCII detection succeeded; `GetModuleHandleW` and `GetModuleFileNameW` confirmed the already loaded DLL's compiler-tree path. The two copies originate from the same compiler archive, so this does not test an incompatible version; it demonstrates that the previous clean-process origin test does not establish protection against a previously loaded same-named module. The disposable package copy remains under `.m0` for inspection. This is a failed isolation subcase, not an N1 pass.

MinGW `objdump -p` recorded direct imports of `libgcc_s_seh-1.dll` and `libstdc++-6.dll` from the extension, and `libwinpthread-1.dll` from both runtime DLLs, alongside `python313.dll` and Windows CRT/platform imports. This is a static import inventory, not a complete runtime trace. The compiler archive includes GCC runtime-exception and winpthreads license texts, but presence of those texts alone does not resolve source, notice, redistribution or compatibility obligations. A release candidate needs an explicit reviewed inventory and compliance determination for the exact binaries.

Next, investigate a collision-resistant closure (including its transitive imports), test deliberate same-name preloads and hostile lookup paths, and trace every loaded module. Do not ship or declare a bundled wheel complete based on copying DLLs beside the extension. The clean independent build, metadata/encoding coverage and the rest of N1–N6 remain outstanding.

## Reusable native job helper — 2026-11-06

`scripts/windows-m0-native-helper.c` exposes a small Win32 interface to create a kill-on-close job, start a process with creation-time job assignment and an explicit Unicode environment, query the active-process count and close handles. It refuses non-absolute local executable and working-directory paths, does not inherit handles, and fails rather than launching outside the job. `scripts/windows_m0_job.py` wraps those operations for the future Python controller and requires the caller to supply paths and the child environment explicitly. The caller still owns private-path policy, environment sanitization, quiescence serialization and process-handle lifetime.

`scripts/windows-m0-native-helper.ps1` built the helper with the workspace-local compiler and exercised the Python adapter: a private Python worker received the explicit environment, started a grandchild, and both were confirmed in the job and exited when it closed. A static import inspection found Windows platform DLLs only. This is a local M0 implementation and check, not the completed N3 gate: the controller does not yet use it, and crash-generation journaling, old-run fencing, phase failures and cross-session recovery remain outstanding. N1–N6 remain pending.

The same helper now exposes a profile-file lock and `windows_m0_job.ProfileLock` holds its handle for the owner's lifetime. It takes an exclusive nonblocking Windows byte-range lock, disallows deletion sharing and refuses a reparse-point lock file. In a same-session check, a second process could not acquire the lock while the owner lived and could acquire it after that owner was terminated. The containing profile directory's private ACL is the caller's responsibility. Cross-session and different-account behavior, secure named-pipe activation and controller integration remain unimplemented or unverified, so N2 remains pending.

`scripts/windows_m0_ledger.py` adds the M0 versioned SQLite intent record. Enqueue commits before returning, conflicting duplicate keys fail, running jobs carry a generation, and interrupted jobs move to review rather than being replayed automatically. Requeue or completion from review requires an explicit reconciliation result; the ledger itself neither verifies library state nor deletes an input. The focused restart check passed on Windows and Linux, including process interruption and input retention.
